# 改写对照与词表

配合 `SKILL.md` 使用。这里收录具体病句的改法和词汇处理规则。

## 术语处理（最高优先级）

三种处理方式，按优先级选择：

1. **换成日常说法。** 能用普通话说的，不造术语。
2. **缩写展开加解释。** 格式：`全称（中文含义，关键属性）`。解释里要给单位、默认值、取值范围中读者需要用到的部分。
3. **内部名词给职责。** 项目代号、模块名、服务名第一次出现时，用一句话说明它是做什么的，不假设读者认识。

示例：

| 病句 | 改法 |
|---|---|
| 修改 TTL 后生效。 | 在 `config.yaml` 的 `cache.ttl` 字段设置缓存存活时间，单位秒，默认 3600。 |
| 本服务依赖 BFF 下发的用户上下文。 | 本服务依赖 BFF（Backend For Frontend，面向前端聚合数据的中间层）下发的用户上下文。后文直接用 BFF。 |
| 数据会流入 ODPS 做离线分析。 | 数据会写入 ODPS（阿里云大数据计算服务）做离线分析。 |
| 点"确认"后触发工作流引擎。 | 点"确认"后，工作流引擎（负责按流程图调度各审批节点）开始执行。 |

反面规则：不要把所有缩写都展开成教科书。Git、HTTP、JSON 这类目标读者已知的词不必解释。判断标准是读者群的中位数水平，不是最低水平。

## 空话、过渡与升华

| 病句 | 改法 |
|---|---|
| 在当今微服务架构日益普及的背景下，可观测性变得越来越重要。 | 本服务用 OpenTelemetry 上报链路数据。 |
| 通过本次优化，不仅提升了系统性能，也为后续扩展打下了坚实基础。 | 优化后，P99 延迟从 480ms 降到 120ms。 |
| 该方案具有高性能、高可用、易扩展的特点。 | 该方案支持水平扩容；单节点故障时读写不受影响。 |
| 值得注意的是，缓存失效时请求会直接打到数据库。 | 缓存失效时，请求直接打到数据库。 |
| 需要强调的是，该接口不支持并发调用。 | 该接口不支持并发调用。 |
| 综上所述，推荐使用方案 B。 | 推荐方案 B：少一次网络往返。 |
| 接下来，我们将介绍部署流程。 | （直接进入部署流程，删掉这句） |
| 本指南旨在帮助开发者快速上手配置系统。 | （删掉，第一段直接写第一条配置） |

判断技巧：把句子里的具体名词（服务名、字段名、数字）圈出来。一个都没圈到的句子，多半可以删。

## 翻译腔与名词化

| 病句 | 改法 |
|---|---|
| 我们需要对日志进行收集与分析，从而实现对问题的快速定位。 | 服务把日志写入 Loki；排查时按 TraceID 查询。 |
| 这是一个用于处理用户登录请求的新的中间件。 | 这个新中间件处理用户登录请求。 |
| 当配置发生变化的时候，服务会被重启。 | 配置变化时，服务自动重启。 |
| 关于超时时间的问题，需要根据实际情况进行调整。 | 超时时间按网络延迟设置，默认 3s。 |
| 错误会被系统记录到日志中。 | 系统把错误写进日志。 |
| 为了能够对请求进行限流，我们引入了令牌桶算法。 | 限流用令牌桶算法。 |
| 在性能方面，新版本表现出显著的优越性。 | 新版本的 P99 延迟从 480ms 降到 120ms。 |
| 该模块具备良好的可扩展性。 | 该模块通过插件接入新协议，不用改核心代码。 |

常见空转动词清单：进行、实现、实施、开展、推动、起到、发挥、具备、拥有、旨在、致力于、聚焦于、围绕、进一步、从而、进而、有效、极大、显著。

处理方式只有两种：删掉，或换成具体动词。

## 指代不清

| 病句 | 改法 |
|---|---|
| 网关把请求转发给订单服务，它超时后会重试。 | 网关把请求转发给订单服务；订单服务超时后重试。 |
| 配置合并时会覆盖默认值，这会导致启动失败。 | 配置合并时会覆盖默认值，覆盖后的值非法时服务启动失败。 |
| 该字段的值是它的默认值。 | 该字段默认值为 3600。 |

规则：一句话里出现两个同类事物时，后面不要用"它 / 该 / 此 / 其"，重说名词，多写几个字不丢人。

## 词表

### 直接删

众所周知、显而易见、毋庸置疑、需要说明的是、值得注意的是、值得强调的是、不难发现、由此可见、总而言之、综上所述、总的来说、接下来、让我们、正如你所见、如上所述（引用很长时除外）。

"首先 / 其次 / 最后"只在真正按顺序讲步骤时保留；两项内容不要用三段式。

### 替换为具体事实

| 词 | 处理 |
|---|---|
| 赋能 | 说清提供了什么能力，或直接写动作 |
| 闭环 | 说清起点、终点和中间步骤 |
| 抓手 | 写具体措施 |
| 沉淀 | 保存、记录下来 |
| 对齐、拉通 | 确认一致、协调 |
| 落地 | 实现、上线 |
| 一站式 | 统一、集中，并说明覆盖范围 |
| 全方位、多维度 | 说明覆盖哪几个方面 |
| 高效、稳定、灵活、强大、可靠、健壮 | 给数字或可验证的行为 |
| 有效地、极大地、显著地 | 删，或给数字 |
| 进一步、从而、进而 | 删，或把因果写明确 |
| 助力、护航、保驾 | 删 |
| 开启新篇章、迈上新台阶、注入新动力、描绘新蓝图 | 删 |
| 具有较强的……性 | 写具体表现，如"支持 1000 并发" |

### 助手痕迹（直接删）

- 以下是……的介绍
- 本文将介绍…… / 本指南旨在…… → 直接开始写内容
- 希望本文对你有帮助
- 让我们深入了解一下
- 需要注意的是
- 如你所见

## 标点与排版

- 破折号只在真正的解释或话题转折处用，一段最多一处。
- 引号统一用中文引号""，代码、字段、命令用反引号。
- 不要用 emoji 当项目符号或分类标记。
- 加粗只用于读者需要跳读定位的关键词，不逐段出现。

## 不要过度纠正

以下情况不属于病灶，不要改：

- 单独一个短句起强调作用没问题，连续三个短句才是问题。
- 引用、标题、报错原文、代码注释里的词。
- 迁移文档、更新日志里对旧行为的描述，这是必要语境。
- 严肃的限制条件、安全说明、法律措辞。
- 正式表达不等于坏表达，只有不承载信息的表达才需要删。
- 术语在目标读者中已是常识的，不必展开。
