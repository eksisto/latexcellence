# 中文技术文档写作

## 目标

让没参与开发的人读一遍就能懂。判断标准只有一条：读者读完知道发生了什么、该做什么，不需要回读。

本 skill 只管语言层：句子、用词、术语、语气。不负责章节划分和文档结构，除非用户明确要求。

## 三条硬规则

1. **不承载信息的句子，删。** 过渡句、总结句、意义升华句、强调句通常都不承载信息。判断方法：删掉之后读者知道的事实变少了吗？没变少就删。
2. **名词在第一次出现时必须落地。** 缩写给全称，内部术语给一句话解释，能用日常说法就换。详见 `references/rewrite-examples.md` 的术语处理一节。
3. **事实不增不减。** 改写时不得添加原文没有的数字、名称、结论，也不得丢失。宁可保留一句不完美的原文，也不编一句通顺的空话。

## 句子规则

- 一句话说一件事。中文技术文档平均句长控制在 25 字以内；超过 50 字必须拆。
- 主语和动作明确：谁做了什么。"服务会重试"，不写"会进行重试"。
- 主动语态优先。"系统把错误写进日志"，不写"错误被系统记录"。
- 代词只在指代唯一时使用。"网关把请求转发给订单服务，它超时后会重试"，"它"指谁？重说名词。
- 动词优先于名词化。"优化配置"，不写"对配置进行优化"；"支持分页"，不写"实现了对分页的支持"。
- 少用"的"。"这是一个用于处理登录请求的新的中间件"改成"这个新中间件处理登录请求"。
- 段落首句给结论或事实，不铺垫。段落第一句不要重复它上面的标题。
- 相邻三句不要用同一个主语开头，换主语或改句式。
- 一段只讲一件事，超过五六行就考虑拆段。

## 用词规则

- 能用数字就不用形容词。"性能显著提升"改成"P99 延迟从 480ms 降到 120ms"。
- 能用具体名词就不用抽象名词。"相关配置"改成是哪个文件、哪个字段。
- 一个概念全文只用一个词。定了"重试"，别处就不要换成"重发"或"再次尝试"。
- 术语超过 5 个且分散出现，在文末补一段术语表。这是语言层补救，不是结构设计。
- 中英文混排时，中英文之间加空格，标点用全角；项目已有排版规范时从其规范。

## 高频病灶

完整清单和改写对照见 `references/rewrite-examples.md`。出现频率最高的几类：

- 空话开头：在当今……的背景下 / 随着……的不断发展
- 意义升华结尾：不仅……也为……打下了坚实的基础
- 强调标记：值得注意的是 / 需要强调的是 / 不难发现
- 总结标记：综上所述 / 总而言之 / 总的来说
- 空转动词：进行 / 实现 / 起到 / 进一步 / 从而 / 有效 / 极大地
- 黑话：赋能 / 闭环 / 抓手 / 沉淀 / 对齐 / 拉通 / 落地 / 一站式
- 空洞形容词：高效 / 稳定 / 灵活 / 强大 / 全方位 / 多维度

## 改写工作流

1. **通读全文**，标记四类问题：不承载信息的句子；未解释的名词；指代不清处；结论被埋在段落中间或末尾的地方。
2. **逐段处理**，原则是"能删不换，能换不改"：
   - 先删：空话、过渡、升华
   - 再换：术语、翻译腔、含糊代词
   - 最后拆：长句、多层嵌套
   - 不重排章节，不合并或拆分小节，那是结构问题，不在本 skill 范围内
3. **事实复核**：逐句核对改写前后的事实，数字、名称、范围、条件不能多也不能少。
4. **交付时**说明改了哪几类问题；删除幅度大时，把删掉的句子单独列出来供用户确认，它们可能含有用户想保留的信息。

## 交付前检查清单

- [ ] 每句话删掉后，读者知道的事实是否变少；没变少的都已经删除
- [ ] 所有缩写、内部术语、新概念都在首次出现处解释过
- [ ] 每个"它 / 该 / 此 / 其"都只有一种指代可能
- [ ] "进行 / 实现 / 起到 / 进一步 / 从而 / 有效 / 显著 / 极大"已逐句检查并处理
- [ ] 每段首句直接给结论或事实，而非铺垫
- [ ] 数字和断言与原文逐条一致，没有新增或丢失
- [ ] 朗读一遍，不像人话的地方重写

## 边界与例外

- 引用、报错原文、代码块、日志、术语定义、法律与安全措辞：不动。
- 迁移文档、更新日志里提到旧行为：是必要语境，保留。
- 限制条件、风险、权衡、适用范围：保留，不要因为它们"显得啰嗦"而删。
- 断句太碎也是毛病：连续三个短句就合并。
- 标题直接写内容，不写"为什么……""如何理解……"这类悬念（FAQ 除外）。
- 改写他人文本但可联系到作者时，先给出修改前后对照，不直接覆盖原文。
- 不确定某句是否承载信息时，保留并询问用户，不要自行删除。
