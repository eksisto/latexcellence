# 技术写作

## 目标与适用范围

让没参与开发的人读一遍就能懂。判断标准只有一条：读者读完知道发生了什么、该做什么，不需要回读。

本 skill 只管语言层：句子、用词、术语、语气、模式。不负责章节划分和文档结构，除非用户明确要求。

与其他 skill 的分工：

- 项目文档的新建与更新流程见 `maintain-latexcellence-docs`。
- commit message 的格式（type/scope）见 `latexcellence-commit-message`。其中描述文字按本 skill 书写。
- 后端英文错误消息按 strict 模式书写。短句、主动语态、常用词，能让 `latexcellence-i18n-errors` 链路的三语翻译更准。

## 第一步：定模式

| 文本类型 | 模式 |
|---|---|
| 流程、runbook、操作步骤、故障排查 | strict |
| 错误、警告、提示（含 HTTPException `detail`、SSE `message`） | strict |
| README、设计文档 | STE-flavored |

- 一篇文档可以混用两种模式。按段落所属的文本类型逐段判定：安装步骤用 strict，概述段落用 STE-flavored。
- 判定不了时用 STE-flavored。

两种模式的共同纪律：主动语态、动词做动作、句长上限、一段一主题、一词一义。不承载信息的句子，删。营销形容词和空洞形容词任何模式都禁止。

- **strict** 执行全部规则：不用缩写（专有技术名如 HTTP、JSON 按名称使用，首次给全称）、短词优先、不用分号。
- **STE-flavored** 放宽词汇限制：技术缩写可用（首次出现给全称），词汇选择以自然为准。句式纪律不放宽。

## 内容硬规则

1. **不承载信息的句子，删。** 过渡句、总结句、意义升华句、强调句通常都不承载信息。判断方法：删掉之后读者知道的事实变少了吗？没变少就删。
2. **事实不增不减。** 改写时不得添加原文没有的数字、名称、结论，也不得丢失。宁可保留一句不完美的原文，也不编一句通顺的空话。

## 句子规则

- 一句话说一件事。中文：指令句（告诉读者做什么）≤25 字，描述句 ≤30 字。英文：指令句 ≤20 词，描述句 ≤25 词。超了就拆句。
- 主动语态。"The parser replaces markers"，不写 "Markers are replaced by the parser"。中文少用"被"字句，让主语做事。
- 动词做动作，不名词化。不说 perform an analysis，说 analyze。中文不说"进行分析/进行优化"，直接说"分析/优化"。短语动词换简单动词（carry out → do）。
- 不堆叠助动词。"should be able to be recovered" 改成 "you can recover"。"应该能够被恢复"改成"可以恢复"。
- -ing 不做主动词。"is checking" 改成 "checks"。
- 不用分号。分号把两条指令粘成一句，读者要自己拆。英文 `;` 和中文 `；` 都不用，改用句号。
- 一段一主题，≤6 句。段内句子讲同一件事，超过就拆段。段落首句给结论或事实，不铺垫，不重复上面的标题。
- 相邻三句不要用同一个主语开头，换主语或改句式。

## 用词规则

- **一词一义。** 同一事物全文只用一个名字。英文定了 "project" 就不换用 "workspace"。中文定了"项目"就不换用"工程"。
- **短词优先。** 用 start，不用 commence。用 use，不用 utilize / leverage。中文用日常词，不用书面腔（"予以""加以""系"）。
- **禁营销形容词与空洞形容词。** 英文禁 seamless、robust、powerful、cutting-edge、advanced。中文禁"无缝、强大、极致、领先、完美、高效、稳定、灵活"。删掉之后信息不变，就说明它们本来就不该在。
- **缩写与术语落地。** strict 不造缩写、不用非必要缩写。STE-flavored 可用缩写。读者可能不熟的缩写、内部术语，首次出现给全称或一句话解释，能用日常说法就换。详见 `references/rewrite-examples.md` 的术语处理一节。
- 能用数字就不用形容词。"性能显著提升"改成"P99 延迟从 480ms 降到 120ms"。
- 能用具体名词就不用抽象名词。"相关配置"改成是哪个文件、哪个字段。
- 术语超过 5 个且分散出现，在文末补一段术语表。这是语言层补救，不是结构设计。

## 中文细则

- 少用"的"。"这是一个用于处理登录请求的新的中间件"改成"这个新中间件处理登录请求"。
- 代词只在指代唯一时使用。"网关把请求转发给订单服务，它超时后会重试"，"它"指谁？重说名词。
- 中英文混排时，中英文之间加空格，标点用全角。项目已有排版规范时从其规范。

## 高频病灶

具体病句和改写对照见 `references/rewrite-examples.md`。出现频率最高的几类：

- 空话开头：在当今……的背景下 / 随着……的不断发展
- 意义升华结尾：不仅……也为……打下了坚实的基础
- 强调标记：值得注意的是 / 需要强调的是 / 不难发现
- 总结标记：综上所述 / 总而言之 / 总的来说
- 空转动词：进行 / 实现 / 起到 / 进一步 / 从而 / 有效 / 极大地
- 黑话：赋能 / 闭环 / 抓手 / 沉淀 / 对齐 / 拉通 / 落地 / 一站式
- 营销与空洞形容词：无缝 / 强大 / 极致 / 领先 / 完美，以及 seamless / robust / powerful / cutting-edge

## 改写工作流

1. **定模式**：按判定表选 strict 或 STE-flavored。
2. **通读全文**，标记问题：不承载信息的句子。未落地、未解释的名词。指代不清处。被动句、名词化、营销词。结论被埋在段落中间或末尾的地方。
3. **逐段处理**，原则是"能删不换，能换不改"：
   - 先删：空话、过渡、升华
   - 再换：术语、翻译腔、含糊代词、被动与名词化
   - 最后拆：长句、多层嵌套
   - 不重排章节，不合并或拆分小节，那是结构问题，不在本 skill 范围内
4. **事实复核**：逐句核对改写前后的事实。数字、名称、范围、条件不能多也不能少。
5. **交付时**说明改了哪几类问题。删除幅度大时，把删掉的句子单独列出来供用户确认。它们可能含有用户想保留的信息。

## 交付前自检

- [ ] 每句话删掉后，读者知道的事实是否变少。没变少的都已经删除
- [ ] 所有缩写、内部术语、新概念都在首次出现处解释过
- [ ] 每个"它 / 该 / 此 / 其"都只有一种指代可能
- [ ] 被动句改成了主动句。名词化、-ing 主动词、短语动词换成了简单动词
- [ ] 超过句长上限的句子拆开了。分号换成了句号
- [ ] 同一事物只用了一个名字
- [ ] "进行 / 实现 / 从而 / 有效 / 显著 / 极大"已逐句检查并处理
- [ ] 没有营销形容词和空洞形容词
- [ ] 每段只有一个主题，不超过 6 句，段首句直接给结论或事实
- [ ] 数字和断言与原文逐条一致，没有新增或丢失
- [ ] 朗读一遍，不像人话的地方重写

## 示例

**英文（strict，runbook 句）**

- 改前：`The service seamlessly leverages an advanced retry mechanism to robustly perform exponential backoff for the handling of API rate limits.`
- 改后：`The service retries failed API calls. It waits longer after each failure. This handles rate limits.`

改动：删营销词 seamlessly / advanced / robustly。leverage 的语义并入 retries。perform ... handling 换回动词 handles。一句拆三句，每句一条信息。

**中文（STE-flavored，README 句）**

- 改前：`系统会对配置文件进行无缝的热重载处理，从而实现对服务稳定性的有效保障。`
- 改后：`修改配置后，系统重新加载配置，服务不中断。`

改动：删"对……进行……处理"的名词化。删营销词与空话（无缝、有效保障、从而实现）。保留主动语态。

**错误消息（strict）**

- 改前：`An unexpected error has occurred while attempting to perform the initialization of the project configuration.`
- 改后：`Failed to initialize project configuration. Check that config.json exists.`

改动：删堆叠助动词（has occurred while attempting to perform）。initialization 名词化改回动词。补一条读者能执行的指令。错误消息说清两件事：出了什么问题，读者下一步做什么。

## 边界与例外

- 引用、报错原文、代码块、日志、术语定义、法律与安全措辞：不动。
- 迁移文档、更新日志里提到旧行为：是必要语境，保留。
- 限制条件、风险、权衡、适用范围：保留，不要因为它们"显得啰嗦"而删。
- 断句太碎也是毛病：连续三个短句就合并。
- 标题直接写内容，不写"为什么……""如何理解……"这类悬念（FAQ 除外）。
- 改写他人文本但可联系到作者时，先给出修改前后对照，不直接覆盖原文。
- 不确定某句是否承载信息时，保留并询问用户，不要自行删除。
