# 维护 LateXcellence 文档

## 概述

LateXcellence 的文档必须保持准确、完整且易于维护。本 skill 强制执行「文档优先」纪律：描述代码变更的文档被修正之前，该变更不算完成。

**核心原则：**

- **代码是事实源。** 文档与代码冲突时，先修文档；若是代码缺陷导致文档与设计不符，则连代码一起修。
- **一次变更，一次文档更新。** 新功能、新模块、配置变更或依赖变更必须反映到对应的文档中。
- **禁止硬编码数量。** 不要写「13 个模块」「14 个页面」等，改用模糊表述或目录引用。
- **对新成员友好。** 每份文档都应帮助新成员理解项目、构建项目并找到正确的模块。

## 适用时机

凡出现以下情况，使用本 skill：

- 新增、删除或重命名后端/前端模块或文件
- 修改 `config.json` / `config.example.json` 的结构或默认值
- 新增或移除依赖
- 变更 API 端点、SSE 事件或错误消息
- 新增功能开关
- 修改构建、部署或启动步骤
- 编写或评审任何涉及文档的 PR 描述或提交信息
- 被要求「更新文档」或「确保文档同步」
- 某个计划/设计文档已全部实施完毕——将其从计划形态转为可维护的设计参考（见下文「方案文档生命周期」）

## 文档职责

每个文件职责单一，只更新相关的文件。

| 文件 | 职责 | 更新时机 |
| --- | --- | --- |
| `README.md` | 项目简介、快速开始、高层功能、项目结构 | 重大新功能、启动命令变更、项目结构变更 |
| `DEVELOPMENT.md` | 索引 / 指向 `docs/` 下的详细文档 | 新增重要文档文件 |
| `PROJECT_SUMMARY.md` | 项目结构树、功能速查、核心设计要点 | 文件/模块增删或重命名；设计概念变更 |
| `DESIGN.md` | 架构、数据流、算法、技术决策 | 架构变更、新数据流、算法更新 |
| `AGENTS.md` | AI 编程助手规则、约束、约定 | 新增编码规则、约定变更、业务约束变更 |
| `docs/development.md` | 开发者上手：技术栈、目录结构、启动、配置、编码规范 | 技术栈、目录、启动/配置或规范变更 |
| `docs/backend-core.md` | 后端核心模块（config、llm_client、project_manager、utils 等） | 核心模块新增/变更 |
| `docs/frontend.md` | 前端架构、路由、组件、hooks、状态管理 | 新页面/组件/hook、路由变更、i18n 变更 |
| `docs/testing.md` | 测试结构、覆盖范围、测试约定 | 新测试文件、测试约定变更 |
| `docs/modules.md` | 模块索引与跨模块架构概览 | 新增模块、模块交互变更 |
| `docs/modules/<module>.md` | 单模块设计、API、数据流 | 模块行为/API 变更 |
| `THIRD_PARTY_NOTICES.md` | 第三方依赖与许可证 | 新增依赖、许可证变更、捆绑资源变更 |

## 文档维护工作流

### 第 1 步：识别代码变更

完成或评审一次代码变更后，逐项自问：

1. 是否改变了项目结构？→ 更新 `PROJECT_SUMMARY.md` 与 `docs/development.md` 的目录树。
2. 是否改变了核心模块？→ 更新 `docs/backend-core.md` 或 `docs/frontend.md`。
3. 是否改变了功能模块？→ 更新 `docs/modules/<module>.md`，必要时更新 `docs/modules.md`。
4. 是否改变了配置？→ 更新 `docs/development.md` 配置章节、面向用户的 `README.md`，并同步 `config.example.json`。
5. 是否新增/移除依赖？→ 更新 `THIRD_PARTY_NOTICES.md`，必要时更新 `README.md` 技术栈。
6. 是否改变了构建/启动方式？→ 更新 `README.md` 与 `docs/development.md`。

### 第 2 步：对照代码核查

阅读相关代码文件，验证文档中的表述：

- 文件路径与名称正确
- API 端点与方法正确
- 配置默认值与 `backend/core/config.py`、`config.example.json` 一致
- 依赖与 `requirements.txt`、`frontend/package.json` 一致
- 模块对 LLM / Marker / SSE / Function Calling 的使用与文档声明一致
- 没有硬编码的文件、模块、页面或 hook 数量

### 第 3 步：执行「代码优先」规则

如果文档说 X 而代码实际是 Y：

1. 判断 X 是否属于代码未能实现的设计意图。若是，先修代码，再让文档与实现一致。
2. 若 X 只是过时描述，更新文档使其描述 Y。
3. 绝不允许文档声明代码无法做到的行为。

### 第 4 步：只更新该更新的文件

避免内容重复。每条信息只存放在一个权威位置：

- 目录结构 → `PROJECT_SUMMARY.md` + `docs/development.md`
- 模块专属行为 → `docs/modules/<module>.md`
- 跨模块模式 → `docs/modules.md` 或 `DESIGN.md`
- 编码规则 → `AGENTS.md`
- 构建/运行命令 → `README.md` + `docs/development.md`

如果同一事实必须出现在多处，详细版本放在一个文件，其余位置只留简短引用 + 链接。

### 第 5 步：校验

在宣布文档工作完成之前：

- [ ] 修改过的 Python 示例能通过 `python -m py_compile`
- [ ] 修改过的 JS 示例能通过 `node -c`
- [ ] 所有内部 Markdown 链接都指向真实存在的文件
- [ ] 改动过的文档中没有硬编码数量
- [ ] 术语与项目其余文档一致（见下文术语表）
- [ ] 新配置默认值已反映到 `config.example.json`（如适用）
- [ ] 新依赖已反映到 `THIRD_PARTY_NOTICES.md`

## 方案文档生命周期（实施完毕后必须改写）

计划 / 设计方案文档（`*-plan.md`、设计方案、收口方案）记录的是「实施依据与变更对照基线」。**一旦计划全部实施完毕，必须将文档改写为面向维护与查询的设计参考**，不能以原始计划形态长期留存——阶段表、评审记录等过程内容会随开发持续膨胀，而实现形态早已沉淀在常设参考文档（`docs/backend-core.md`、`DESIGN.md`、`docs/modules/<module>.md`、`docs/deployment.md`）中。

**时机**：计划的所有阶段完成、代码合入后（通常在该收口提交中）立即改写，不要拖延。

**删除**（实施后对维护无意义的过程内容）：

- 阶段划分与验收表、实施清单、测试计划、分阶段实施记录（评审修复记录、偏离声明的**实质**应先沉淀进对应常设文档，再从方案文档中删除）
- commit 对照、评审过程叙述、「全局约束（每阶段适用）」、文档同步义务 / 勾销义务清单
- 冗长的状态头（改为一句「状态：已实施」+ 文档定位与冲突裁决说明）

**保留**（持久知识）：

- 背景与动机（为什么这么做）、设计机制、关键决策依据（浓缩为决策表）
- 非目标 / 已知限制——它们是 roadmap 与未来评审的输入，不得删
- 配置结构示例、接口契约、槽位 / 调用点映射等查询型内容

**锚点契约（硬约束）**：大量代码注释以「文档名 §章节」「决策 QN」形式引用方案文档（如 `editor-design.md §5.1`、`决策 Q3`）。改写时：

- 保持文件名与被引用章节的**编号**不变；删除章节后允许编号留空隙，不得为消除空隙而改动被引用的编号
- 决策 Q 表可压缩措辞，但 Q 编号集合必须完整保留
- 确需重命名 / 重编号时，必须全仓库搜索（`.md` / `.py` / `.js` / `.jsx`）逐处同步引用，禁止只改文档本身

**合并与命名**：

- 仅因先后实施而拆分的方案（v1 / v2）应合并为单一权威设计文档；因尚未实施而独立成文的保留独立
- 已实施方案不再使用 `-plan` 后缀：单一主题用裸名（`multi-user.md`、`multi-model.md`），需区分代际 / 主题时用 `-design` 后缀（`editor-design.md`、`editor-productivity-design.md`）；未实施前可暂保留原名

**同步与校验**：改写 / 合并 / 重命名后，同步 `DEVELOPMENT.md`、`PROJECT_SUMMARY.md`、`DESIGN.md` 及其他文档与代码注释中的全部引用，并校验内部链接与 § 锚点全部有效。

**反例（本项目真实教训）**：`multi-user-plan.md` 与 `multi-user-v2-plan.md` 实施完毕后以计划形态长期留存，膨胀至合计 1032 行（含千字级单阶段实施记录段），最终不得不合并精简为 213 行的 `multi-user.md`。方案落地时即改写，成本远低于事后集中清理。

## 硬性规则

以下规则不可妥协，来自 `AGENTS.md` 与项目经验教训。

### 1. 禁止硬编码数量

**错误：**「项目包含 13 个功能模块。」
**正确：**「项目包含多个功能模块，详见 `docs/modules.md`。」

### 2. 禁止未经核实的代码行为声明

每个 API 端点、配置默认值、依赖版本和文件路径，写入文档前必须对照实际代码库核实。

### 3. 新增配置必须同步示例

向 `backend/core/config.py` 添加配置字段时，必须同步更新 `config.example.json`，并在 `docs/development.md` 中说明。

### 4. 新增依赖必须登记

新增 Python 包或 npm 包时，必须在 `THIRD_PARTY_NOTICES.md` 登记版本、许可证与用途。

### 5. 新增功能必须同步界面四处

新增功能模块时，必须更新 `frontend/src/pages/WelcomePage.jsx` 的 `featuresList`、`frontend/src/components/SettingsDialog.jsx` 设置界面，以及 `backend/core/config.py` 的 `AppConfig` / `FeaturesConfig`（按 `AGENTS.md` 的配置同步规则）。

### 6. 新增错误消息必须带翻译

新增后端错误消息字符串时，必须在 `frontend/src/i18n/locales/zh.json` 与 `en.json` 的 `errors` 命名空间下添加条目。

## 常见文档问题

警惕以下红旗信号：

- 文档描述的功能已不存在
- 目录树中列出了已被移动或删除的文件
- 模块文档说「不使用 LLM」但代码在某个路径调用了 LLM
- 文档中的配置默认值与 `config.py` 或 `config.example.json` 不一致
- 某依赖在 `THIRD_PARTY_NOTICES.md` 中缺失
- 同一段解释被原样复制到三个文件
- 文档使用「X 个模块」「Y 个 hook」这类数量表述
- 前端文档描述的 i18n 命名空间数量与 `frontend/src/i18n/index.js` 不符
- 已实施的方案文档仍保留阶段验收表、commit 对照或分阶段实施记录
- 文档仍叫 `*-plan.md`，而它规划的功能早已全部实施
- 方案文档被改写后，代码注释中的锚点（`文档名 §N` / `决策 QN`）已经悬空

## 如何评审文档变更

像评审代码一样评审文档变更：

1. **正确性：** 是否与代码一致？
2. **完整性：** 新成员能否据此获得足够信息？
3. **单一事实源：** 是否存在不必要的重复？
4. **术语：** 是否与术语表一致？
5. **数量：** 是否有硬编码数量？
6. **链接：** 内部链接是否有效？
7. **示例：** 代码片段能否通过编译？
8. **方案生命周期：** 若文档是已实施完毕的方案，是否已按「方案文档生命周期」转为设计参考并保住锚点？

使用以下严重级别：

- **Critical（严重）：** 文档声明了代码未实现的行为，或违反硬性规则
- **Required（必须修）：** 过时/不完整的信息，必须修正
- **Optional（可选）：** 措辞、顺序或格式改进
- **Nit（吹毛求疵）：** 错别字、轻微表述问题
